# 設計書のレビューの観点

設計書（docs/design/）をレビューするときの観点と指摘の書式。レビューのたびに観点が変わると前の回と結果を比べられず、修正したあとの穴を見落とす。毎回下の観点を全部この順に見る

## 渡す資料

- 読むのは docs/design/ の全部のファイル、CLAUDE.md、このファイルだけ。前の回の指摘と修正した内容は渡さない ── 前の回の結論に引きずられない
- 外部のツールと API の記述は一次資料（GitHub Docs、Claude Code の docs、gh の manual、git の文書）で確かめる
- 修正箇所の確認（下）は別の扱いで、その回の指摘と修正した内容を渡す

## 観点

### 認証情報と権限

- 守る認証情報（`CLAUDE_CODE_OAUTH_TOKEN`、`GITHUB_TOKEN`、PR 用トークン、App の秘密鍵、導入する側の準備の step が置いた認証情報）に Claude Code か、Claude Code が書いたコードがアクセスできる経路が無いか
- Claude Code が触ったあとの作業ディレクトリは攻撃する側が内容を決められるものとして見る
- ジョブの境界（artifact、キャッシュ、環境変数、git の設定、step の出力、ログ）を越えて埋め込んだものが受け渡されないか
- 各ジョブとトークンの権限が使う操作に対して不足していないか、過剰でないか

### ゲートを外す経路

- Claude Code かゲートのコードが、ゲート、Claude Code の設定、テスト、自動マージの範囲を変えられないか
- テスト作成を含む各工程が判定の材料（既存のテスト、テスト・lint・ミューテーションテストの設定）を弱められないか
- パスで判定するところは次の場合も見る: まだ無いパスを新しく作る、下の階層に置く、名前を変える、シンボリックリンク、git の管理の外のファイル、ignore されたファイル
- 作業のジョブの検査が飛ばされても提出のジョブと CI で止まるか

### 外から来る文面と時刻のずれ

- 外部の投稿者が触れる入力（Issue のタイトルと本文、コメント、テンプレート、CI のログ、テストの出力）がどの工程に渡るか
- 確かめたあとに内容が変わる隙間（ラベルのあとの編集、実行待ちの間の変化、2つのジョブのすれ違い）が無いか
- 外部の投稿者が数で仕組みを止められないか（実行待ちの上限、コスト）

### 記述と動作の一致

- GitHub Actions、GitHub の API、Claude Code、gh、git について書いたことが一次資料と合っているか
- 権限の名前、イベントの名前、API のフィールドの名前が実在するか

### 終わり方の網羅

- 各ジョブと各工程の終わり方（成功、変更なし、失敗、取り消し、飛ばされた、上限、時間切れ）がどれも人への引き継ぎの表の理由か、マージに結びつくか
- 引き継ぎの理由ごとに人が次にやることが決まっているか
- 判定の表でレポートとゲートの結果の組み合わせのどれにも次の工程が決まっているか

### 節どうしの食い違い

- 同じものを書いた箇所どうしが合っているか: ジョブの表、トークンと権限、App に付ける権限、入力、変数、上限の表、引き継ぎの表、検査のタイミングの表、用語の表、CLAUDE.md の引き継ぎの理由の一覧

### CLAUDE.md の原則

- 原則（コマンドで決まるものはコマンドで決める、自己申告を合否に使わない、Claude Code が自分のゲートを外せない、決まらなければ止める）を破っていないか
- 検査のタイミングの決まり（ツール呼び出しごとは照合だけ、安い順、結果が変わらない検査は1回）を破っていないか

### 使いやすさ

- 導入の手間、既定値で動くか、人の操作の数、速さ、やり直しのしやすさを守りのために崩していないか

### 用語と根拠

- 用語の表の「使わない言い方」、口語、同じものを2つの言い方で呼ぶ箇所が無いか
- 事実の記述に根拠（出典の範囲、または「推論のみ」）が付いているか

### 未決の残り

- 「実装のときに確かめること」に資料を読めば今決められるものが残っていないか

## 観点の外

上の観点に当てはまらない問題を見つけたら「観点の外」として報告する ── 観点の一覧を見てよい範囲の一覧として扱わない。同じ種類の指摘が観点の外で続いたらこのファイルに観点を追加する

## 重大度

| 重大度 | 基準 |
|---|---|
| critical | 認証情報が漏れる、範囲の外の変更がマージされる、ゲートを外せる |
| major | 書いたとおりに動かない、人に知らせずに終わる |
| medium | 特定の条件のときだけ崩れる、節どうしが食い違う |
| minor | 用語と書き方、根拠の不足 |

### 数える指摘の条件

critical と major のうち固めるかの判断に数えるのは次の両方に当てはまるものだけ ── 机の上で読むだけのレビューでは動かせば判明することまで探すと終わらない

- 想定する攻撃の中で起きる ── security.md の「守る対象」の想定する攻撃に入る。想定しないもの（書き込み権限を持つ人の悪意など）は数えない
- 失敗の筋書きが一次資料に書かれた動きだけで成り立つ ── 「推論のみ」「未確認」の動きに頼る筋書きは数えない

設計書の「実装のときに確かめること」に挙げてあり、確かめた結果ごとの扱いが書いてあるものもそれだけでは数えない

数えないものも捨てない。「実装のときに確かめること」か「実装のあとで試すこと」に確かめ方と、成り立ったときの扱いを書いて閉じる

### 種類

数える指摘は既に塞いだ種類か、新しい種類かに分ける

- 既に塞いだ種類: 修正方法が設計書に既にある一覧に追加するか、既にある仕組みの対象を広げるだけで済む
  - 一覧の例: 固定の除外ファイル、許すツールの名前、守りの環境変数
  - 仕組みの例: 作業ツリーを戻す処理、Claude Code を呼び出す前の照合
- 新しい種類: 新しい仕組みが要る

## 指摘の書式

重い順に並べ、1件ごとに次を書く

- ID と重大度
- 観点（上の見出しの名前か「観点の外」）
- 場所: 設計書のファイル名と見出しと、探せる短い引用
- 欠陥: 1〜2文
- 失敗の筋書き: どの入力と状態のときに何が起きるか
- 根拠: URL とそこに書かれていること、「推論のみ」、「未確認」のどれか
- 修正方法: 1〜2文
- critical と major にはさらに次の2つ
  - 数えるか: 数える、数えない、のどちらかと理由（想定する攻撃の中か、一次資料だけで成り立つか）
  - 種類: 既に塞いだ種類（広げる一覧か仕組みの名前）か、新しい種類か

最後に疑ったが問題なかったものを1行ずつ書く

## 除外した指摘

受け取った側が確かめて誤りだった指摘は理由を1行添えて除外する。除外した指摘は数えない

## 設計を固める基準

次のどれかで設計を固めて実装に進む。どの終わり方でも medium 以下はその回で修正する

- 数える critical と major が0件の回が出た
- 数える critical と major がどれも既に塞いだ種類だった ── その回で修正し、修正箇所の確認を経て固める
- 8回目の全体のレビューを終えた（全体のレビューは8回まで）── その回の指摘を修正し、修正箇所の確認を経て固める。指摘が全部除外した指摘なら修正するものが無いのでそのまま固める

## 修正箇所の確認

固める前にその回の critical と major を修正した箇所を新しいエージェントに見せる。全体のレビューはしない

- 渡す資料: その回の critical と major の指摘、修正した内容、docs/design/ の全部のファイル、CLAUDE.md、このファイル ── 前の回の指摘を渡さない決まりは全体のレビューにだけ当てる
- 確認する点: 塞がっているか。修正が新しい critical を生んでいないか
- 穴が見つかったら修正してもう1回だけ確かめる。2回目でも穴があれば results.md の「試験結果」にまだ試していない項目として移して固める ── 確認はどの回でも2回まで
