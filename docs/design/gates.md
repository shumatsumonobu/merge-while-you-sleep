# 合否の判定

変更の合否をコマンドと [Claude Code](https://code.claude.com/docs) のどちらがどう決めるか。設計書の入口は [README.md](README.md)

## ゲート

ゲートはコマンドの終了コードで合否を決める検査。この節で使う語

- 着手前のゲート: Claude Code を呼び出す前に基準コミット（作業を始める、default ブランチのコミット）のままでテスト、lint、型検査が成功するかを確かめるゲート
- 失敗の確認: 実装の前に、新しく書いたテストが失敗することを確かめるゲート
- テストの凍結: 実装と修正の工程にテストのファイルを変更させないこと
- ツリー: git の tree オブジェクト。ある時点のファイルの一式

| ゲート | いつ | 確かめること |
|---|---|---|
| 着手前のゲート | 作業のジョブの最初。Claude Code を呼び出す前 | 基準コミットでテスト、lint、型検査のコマンドが成功すること |
| テスト作成の変更範囲 | テスト作成のあと | テスト作成の工程で変えたのが新しく作ったテストのファイルだけであること |
| 失敗の確認 | テスト作成のあと | この実行で書いたテストのファイルだけを基準コミットに追加したツリーで、テストのコマンドが失敗すること |
| 変更禁止ファイル | Claude Code を呼び出す前に毎回 | 変更禁止ファイルが作業の最初から変わっておらず、増えてもいないこと |
| テストの凍結 | 実装と修正のあと | 実装と修正の工程でテストのファイルを変更も追加も削除もしていないこと |
| テスト | 実装と修正のあと | 対象プロジェクトのテストのコマンドが成功すること |
| lint | 実装と修正のあと | 対象プロジェクトの lint のコマンドが成功すること |
| 型検査 | 実装と修正のあと | 対象プロジェクトの型検査のコマンドが成功すること |
| 既存のテストだけのツリー | 実装と修正のあと | この実行で追加したテストのファイルを除いたツリーで、テストのコマンドが成功すること |
| ミューテーションテスト（入れるときだけ） | レビューが承認したあと | 入力で渡したコマンドが成功すること |
| 自動マージの範囲 | 提出のジョブ | 基準コミットとの差分全体のパスがすべて自動マージの範囲に入っていること（[自動マージの範囲](#自動マージの範囲)） |
| 既存のテスト | 提出のジョブ | 基準コミットにあったテストのファイルを変えても消してもいないこと |

テスト作成の変更範囲

- 基準コミットにあったテストのファイルは変えない
- 見るのは工程の前後のコミットの差分。新しく作ったファイルも含む

失敗の確認

- 見るツリーは基準コミットに、この実行で書いたテストのファイルだけを追加したツリー
- 入力 `test_file_command`（テストのファイルを引数に取るコマンド）を渡したときは新しいテストのファイルごとに失敗すること
- 実装が無いのに成功するテストは採点基準にならない
- `test_file_command` でファイルごとに見るのは、1つのコマンドの終了コードでは新しいテストのどれか1つが失敗したことしか判明せず、内容の無いテストが隠れるから
- 実装のあとにテスト作成に戻ったときも同じツリーで確かめる。ミューテーションテストから戻ったときは除く（[ミューテーションテスト](#ミューテーションテスト)）

変更禁止ファイル

- 下の階層を含む作業ディレクトリ全体を、git の管理の外のファイルも含めてパターンで探し、ハッシュで比べる。`.git` と、入力 `workspace_keep` のディレクトリ（`node_modules` など）の下は探さない ── どちらも Claude Code とゲートからは書き込めない
- 比べる前に Claude Code が自分で作る `.claude/.cc-writes` と、`.claude` の下に新しくできた空のディレクトリを消す ── 中にファイルを置いたら増えたとして止める

テストの凍結

- 対象は基準コミットにあったテストと、テスト作成の工程で書いたテストの両方
- 見るのは工程の前後のコミットの差分

既存のテストだけのツリー

- 新しいテストのファイルが、読み込まれたときに既存のテストの前提を変えて（例: 共有のモジュールを書き換える）、失敗するはずの既存のテストを成功させていないかを見る

ミューテーションテスト

- 実装をわざと壊してもテストが気づくかを見る（[ミューテーションテスト](#ミューテーションテスト)）

### ゲートの実行方法

- ゲートのコマンドは通信と認証情報の無い隔離した環境で実行する ── 扱いは[security.md の「ゲートのコマンドを隔離する」](security.md#ゲートのコマンドを隔離する)
- 実装と修正のあとのゲートは安い順に実行する: テストの凍結 → lint → 型検査 → テスト → 既存のテストだけのツリー。失敗したらそこで止めて修正に戻す
- 作業のジョブの中のゲートは早く修正するための検査 ── 作業のジョブでは Claude Code が shell を使えるので、テストのコマンドも書き換えられうる
- 最後に決めるのは次の2つ
  - 自動マージの範囲と既存のテスト: 提出のジョブ
  - テストの合否: PR に対して新しいマシンで動く CI（必須のステータスチェック）

### Claude Code の呼び出しのあとに残るプロセス

- Claude Code の呼び出しは呼び出しごとに cgroup（Linux でプロセスをまとめて扱う仕組み）にまとめて動かす。終わったら中のプロセスを全部止め、残りが無いことを確かめてから、作業用のコミットを作る
- 理由: sandbox（Claude Code が Bash で起動したコマンドの、読める場所、書ける場所、外への通信先を絞る Claude Code の機能）の中で起動して残ったプロセスが、コミット、照合、ゲートの最中に作業ディレクトリを書き換えないようにする
- 残っていれば守りが働いたとして止める
- sudo で cgroup を作れないときは呼び出す前に無かった、同じユーザーのプロセスを止めることで代替する。GitHub ホストの runner では作れる（[security.md の「Claude Code に認証情報を読ませない」](security.md#claude-code-に認証情報を読ませない)の確認結果）

### 作業用のコミット

- work.mjs は Claude Code の呼び出しが終わるたびにその工程の変更を作業用のコミットにする。新しく作ったファイルも入れ、ignore されたファイルは入れない
- 工程の変更範囲とテストの凍結は、このコミットの間の差分で見る（`git diff --raw --no-renames -z`）
  - 作業ツリーの `git diff` には新しく作ったファイルが含まれない
  - 名前の変更を検出したままだと変える前のパスが含まれない
  - 根拠: [git-diff の文書](https://git-scm.com/docs/git-diff) に `--name-only` は「Show only the name of each changed file in the post-image tree」、`diff.renames` は「Defaults to `true`」
- 提出に渡すのはレビューが最後に承認したコミット ── ミューテーションテストが作業ツリーを変えても渡さない

### 作業ツリーを戻す

ゲートのあとと、作業用のコミットを作ったあとに、作業ツリーを戻す

- 戻すこと: ゲートのあとは作業ツリーをゲートの前のコミットに戻し、変わったファイルを戻す ── ゲートのコードが書いたものを次のコミットに入れない
- 消すもの（`workspace_keep` を除く）: git の管理の外のファイルを、ignore されたものも含めて消す。消すのは `git clean -ffdx`
  - `-f` を2つ付けるのは入れ子の git のリポジトリも消すため（[git-clean の文書](https://git-scm.com/docs/git-clean) に「Git will refuse to modify untracked nested git repositories (directories with a .git subdirectory) unless a second -f is given.」）
  - `workspace_keep` は依存を入れたディレクトリ。入力 `workspace_keep` で決め、既定は `node_modules`、`.venv`、`venv`、`vendor`（[adoption.md の「作業の action（`work`）」](adoption.md#作業の-actionwork)の入力の表）
  - `workspace_keep` として残すのは作業の最初からあるディレクトリだけで、作業の途中で作られたものは消す
- 戻したあとの検査: `git status --porcelain --ignored` を見て、作業の最初からある `workspace_keep` のディレクトリのほかに何か残っていれば、守りが働いたとして止める
- 作業用のコミットを作ったあとも同じく作業ツリーをそのコミットと同じにする ── ignore されたファイルは作業用のコミットに入らず、どの検査の差分にも現れない。Claude Code が ignore されたファイル（例: ignore されている、テストの道具が読む設定のファイル）を置いてもゲートはそれを使わない

依存のディレクトリ

- `workspace_keep` のディレクトリ（`node_modules` など、依存を入れたディレクトリ）は、Claude Code の sandbox でもゲートの中でも読み取りだけにする。使うのは `Edit(<ディレクトリ>/**)` の deny ルール（permission の deny ルールは Claude Code に使わせない操作と対象を書く設定）と、[bubblewrap](https://github.com/containers/bubblewrap) の読み取りだけのマウント
- 理由: 依存の内容（テストの道具そのもの）を書き換えると作業のジョブにしか無いゲート（失敗の確認、既存のテストだけのツリー、ミューテーションテスト）が、sandbox を破らなくても意味を失う
- 依存を追加する変更は依存の定義のファイルが範囲の外なので、いずれにしても人が読む

### 着手前のゲートが失敗した場合

- 着手前のゲートが失敗したら Claude Code を呼び出さずに人に引き継ぐ
- 着手前のゲートの1つのコマンドの時間の上限は30分（決まった値）で、超えたら失敗したとして扱う
- 理由: 基準コミットで失敗するテストがあると、失敗の確認は何を書いても合格し、実装のあとのテストは何をしても成功しない。サブスクの利用枠を使う前に止める

### 変更禁止ファイルが変更された場合

- 変更禁止ファイルが変わったらその場で止めて人に引き継ぎ、PR を作らない ── 次に呼び出す Claude Code が、変わった設定や CLAUDE.md で動くのを防ぐ
- Claude Code を呼び出す前に確かめるのは、`.claude/settings.local.json` のように git の管理の外に置かれるファイルも次の呼び出しで読まれるから
- permission の deny ルール、Claude Code の sandbox、ゲートの隔離が書き込みを止めるので（[security.md の「守り」](security.md#守り)）、通常は起きない。起きたら守りが破られたものとして扱う

### ミューテーションテスト

- ミューテーションテスト（実装をわざと壊してテストが気づくかを確かめる）は、[loop-engineering-playbook](https://github.com/shumatsumonobu/loop-engineering-playbook) から取り入れる考え方
- 既定では実行しない ── 言語ごとに道具が違い、実行に時間がかかる
- 入力でコマンドを渡したときだけレビューが承認したあとに1回実行する（コストの高い検査は最後）
- 失敗したらテスト作成の工程でテストを追加し、ゲートとレビューをもう一度通す。テスト作成に戻す上限（1回）に数える
- このとき失敗の確認は見ず、テストを追加したあとにミューテーションテストをもう一度実行する ── 生き残った変異が基準コミットからある行にあると、それを見つけるテストは基準コミットでも成功するので、失敗の確認のゲートが必ず不合格になる

### テストのファイルの判別

テストのファイルはパターンで見分ける。既定のパターン

```text
**/*.test.*
**/*.spec.*
**/test/**
**/tests/**
**/spec/**
**/__tests__/**
**/test_*.*
**/*_test.*
**/*_spec.*
**/*Test.*
**/*Tests.*
**/__snapshots__/**
**/*.snap
**/testdata/**
**/fixtures/**
**/__fixtures__/**
**/testing/**
**/test-utils.*
**/test_utils.*
**/testUtils.*
**/*.cy.*
```

- スナップショット、テストのデータ、テストが共有する補助のファイルも、既存のものを変えれば既存のテストを変えたことになる
- どの階層にあっても合う書き方にする ── Maven と Gradle の `src/test/java/`、モノレポの `packages/*/test/` のようにテストはルートの階層の外にも置かれる
- パターンに合わないテストと、テストが読み込む補助のファイルは、凍結も既存のテストの確かめもされない ── プロジェクトの置き方に合わせて変数 `MERGE_WHILE_YOU_SLEEP_TEST_PATHS` に書く。変数を書くと既定のパターンは使わず、変数のパターンだけを使う
- テストのパターンは大文字小文字を区別する ── 区別しないと `**/*Test.*` が `src/latest.js` のようなソースのファイルに合い、実装の工程がそのファイルを変えるたびにテストの凍結で失敗する
- 基準コミットにテストのパターンに合うファイルが1つも無ければ、始められないとして止める ── パターンがプロジェクトのテストの置き方と合っていない見込みが高い。変数 `MERGE_WHILE_YOU_SLEEP_TEST_PATHS` で修正する

### 既存のテストを変更させない

- 既存のテストはどの工程にも変更させない。既存のテストに追加したいケースも新しいファイルに書く
- テスト作成の変更範囲が「テストのファイルなら許可する」だと、テスト作成の工程で既存のテストを内容の無い形（例: `expect(true).toBe(true)`）に書き換えても、失敗の確認は新しいテストが失敗すれば通過する
- 凍結が「テスト作成の工程で書いたテスト」だけを見ると実装の工程でも同じことができる
- どちらも最後は提出のジョブで範囲の外になるが、それまでの反復が無駄になり、弱めたテストの PR が人に渡る
- loop-engineering-playbook の proof/README.md の27番（「ワーカーは「今回 触っていない既存のテスト」を実装段階で弱められた」）も凍結が今回変更したテストしか見ていなかった

### テスト作成に戻す

- 実装や修正の工程が「テストが間違っている」と返したらテスト作成の工程に1回だけ戻す ── 実装の工程にはテストを変更させない
- 戻ったテスト作成の工程はこの実行で書いたテストのファイルを修正してよい（基準コミットにあったテストは変えない）

### 作業ディレクトリを分けない

- 作業ディレクトリを分ける仕組み（[git](https://git-scm.com/) の `git worktree`）は持たない ── 各ジョブは新しいマシンで動き、1つのジョブの中で Claude Code は1つずつ動く
- [TAKT](https://github.com/nrslib/takt) が `git worktree` をやめたのは「Claude Code SDK がメインリポジトリに遡らないよう」（TAKT の docs/CHANGELOG.ja.md の 0.2.3）で、この設計には遡る先のリポジトリが無い

制約

- main のテストが失敗している状態を修正する Issue は扱えない ── 着手前のゲートで止まる。人が main を修正してから起動する

## 判定

各工程のあと次にどの工程へ進むかを決める仕組み

判断: 判定は work.mjs のコードで決める。判定のための Claude Code の呼び出しは持たない。各工程の Claude Code は、決まった形の JSON（レポート）を1回の呼び出しで返し（`--json-schema`）、work.mjs がレポートと生データを決まった規則に当てはめて、次の工程を選ぶ

| 工程 | レポートの内容 |
|---|---|
| 計画 | 状態（完了、進められない）、進められない理由（完了条件が足りない、その他）、手順、変更する見込みのファイル |
| テスト作成 | 状態（完了、すでに満たされている、進められない）、進められない理由（完了条件が足りない、その他）、書いたテスト、どの完了条件をどのテストで確かめるか |
| 実装、修正 | 状態（完了、進められない）、進められない理由（完了条件が足りない、テストが間違っている、その他） |
| レビュー | 結論（承認、修正を求める）、指摘の一覧（ID、状態、重大度、場所、根拠、どの完了条件に関わるか）。重大度は「修正が必要」と「提案」の2つ |
| 競合の解消 | 状態（解消した、解けない） |

次の工程の決め方を工程ごとに「条件 → 次の工程」で書く

計画

- 変更禁止ファイルを変える見込み → 実装の前に人に引き継ぐ
- 自動マージの範囲の外を変える見込み → 進捗のコメントにそう書いて進める（提出で自動マージを予約しない）
- 進められない、理由が完了条件が足りない → 完了条件が足りないとして人に引き継ぐ
- 進められない、理由がその他 → 判定が決まらないとして人に引き継ぐ
- それ以外 → テスト作成

テスト作成

- ゲート（テスト作成の変更範囲、失敗の確認）を通過した → 実装
- ゲートが失敗した → ゲートの出力を渡してテスト作成をやり直す（ゲートの失敗の上限に数える）
- 「すでに満たされている」 → 変更が無いとして人に引き継ぐ
- 進められない、理由が完了条件が足りない → 完了条件が足りないとして人に引き継ぐ
- 進められない、理由がその他 → 判定が決まらないとして人に引き継ぐ

実装、修正

- 完了の申告は使わず、ゲートの結果で決める
- ゲートを全部通過した → レビュー
- ゲートが失敗した → ゲートの出力を渡して修正（ゲートの失敗の上限に数える）
- 進められない、理由がテストが間違っている → テスト作成に戻す
- 進められない、理由がそれ以外 → 人に引き継ぐ

レビュー

- 「修正が必要」の指摘が解消せずに残っている → 結論が承認でも修正
- 「提案」の指摘 → 修正に進めず、PR の本文に載せる
- 「修正が必要」の指摘が無いのに、結論が修正を求める → 根拠の無い結論なので、レポートの不備として人に引き継ぐ
- 結論が承認で、「修正が必要」の指摘が無い → ミューテーションテスト（入れるとき）、それから提出
- 差分が20万文字を超える → レビューに渡さずに判定が決まらないとして人に引き継ぐ ── 切って渡すと切った先の変更を見ずに承認しうる

競合の解消

- 解消した → 変更範囲が競合したファイルだけかを確かめて、ゲート
- 解けないか、ほかのファイルを変えていた → 提出のあと自動マージまで進めないとして人に引き継ぐ（[run.md の「再実行」](run.md#再実行)）

TAKT から取り入れる考え方

- 工程の呼び出しと判定を分ける ── 次の工程を、その工程の Claude Code に決めさせない。この設計では判定をコードにして分ける
- 書かれた結論より内容を採る ── 修正に進むかは結論ではなく指摘の一覧で決める。指摘の無い「修正を求める」は従う内容が無いので人に引き継ぐ
- 決まらなければ止める ── レポートがスキーマに合わない、規則のどれにも当てはまらないときは既定の工程に流さずに人に引き継ぐ
- Claude Code の記憶を信用させない ── 指示文で判断の直前にファイルとコマンドの出力を読み直させる
- レビューの指摘に ID を付けて反復をまたいで追う ── 状態は、新規、残っている、解消、再発。前回の指摘の一覧を次のレビューに渡す（TAKT の builtins/ja/facets/partials/policies/review-common.md に「同じ指摘の堂々巡りを防ぐため、指摘をIDで追跡する。」）

理由

- 次の工程を決める材料は、ゲートの終了コード、差分、レビューの指摘の一覧で、どれも決まった形のデータ ── 当てはめはコードでできる。Claude Code に問い合わせる回数が減り、同じ入力なら毎回同じ結果になる
- 判定に生データが混ざる ── 実装の完了の申告ではなく、ゲートの結果で進む
- 呼び出しが減る ── TAKT ではレポートと判定のある工程は、作業、レポート、判定の3回の呼び出しになる（TAKT の CLAUDE.md の Three-phase step model）。この設計では工程ごとに1回
- 作業した本人のレポートだけで決めない ── 実装の工程は別の呼び出しのレビューと、コマンドのゲートで確かめる

制約

- レポートの形（JSON のスキーマ）を工程ごとに持つ ── 形を変えると work.mjs の規則も変える
- 結論と指摘の一覧の食い違いは人に引き継ぐ ── もう一度レビューさせる案より単純。マージまで進んだ6本（測定の5本と、今の版で実行した `review3`）では、どれもレビューが1回目で承認し、起きなかった（[results.md](results.md#測定結果)）
- 指摘の ID を付けるのはレビューの Claude Code ── 同じ問題に別の ID を付けると繰り返しの検知をすり抜ける。そのときは反復の回数の上限で止まる

## 自動マージの範囲

判断: 範囲に入るのは導入する側が決めるパターン（変数 `MERGE_WHILE_YOU_SLEEP_ALLOW_PATHS`。必須）に合うファイルだけ

- そこから固定の除外ファイルと、基準コミットにあったテストのファイルを除く
- 新しく追加したテストのファイルも `MERGE_WHILE_YOU_SLEEP_ALLOW_PATHS` に合うときだけ範囲に入る ── テストの置き場所（例: `tests/**`）は `MERGE_WHILE_YOU_SLEEP_ALLOW_PATHS` に書く
- 範囲の外を変えた実行は PR を作るが自動マージを予約せず、人に引き継ぐ

### 固定の除外ファイル

どの階層にあっても外す。追加できるが、減らせない

| 固定の除外ファイル | 外す理由 |
|---|---|
| `.github/` の下すべて、どの階層の `CODEOWNERS` も | ワークフローを書き換えると自分のゲートを外せる。`CODEOWNERS` を書き換えると人のレビューの必須を外せる |
| Claude Code の決まりのファイル（一覧は表の下） | Claude Code の振る舞いを変える。次の実行の決まりを Claude Code が自分で緩められる |
| テストの設定と、全部のテストに影響するファイル（一覧は表の下） | テストの対象や合否の基準を変えられる |
| lint と型検査の設定（`eslint.config.*`、`.eslintrc*`、`tsconfig*.json`、`mypy.ini`、`ruff.toml` など） | lint と型検査の基準を変えられる |
| 依存とスクリプトの定義（一覧は表の下） | 依存を追加すると外のコードがそのままマージされる |
| git の設定（`.gitattributes`、`.gitmodules`） | git の動作を変えられる |
| どの階層の GEMINI.md も | ほかのコーディングエージェントへの指示。導入先がほかのコーディングエージェントも使っているとその振る舞いを変えられる |

- `CODEOWNERS` は `.github/`、根、`docs/` に置ける（GitHub Docs の [About code owners](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners)）

- work.mjs が作業の最初に基準コミットのこれらのファイルから取り込み先をたどって一覧にする
- 取り込み先が基準コミットにまだ無いパスでも一覧に入れる ── 作られると次の呼び出しから決まりとして読まれる

### 固定の除外ファイルのうち、変更禁止ファイル

- 変更禁止ファイル: `.github/` の下、どの階層の `CODEOWNERS`、CLAUDE.md、CLAUDE.local.md、AGENTS.md、`.claude/` の下、`.mcp.json`、CLAUDE.md と AGENTS.md が `@` で取り込むファイル
- 変更禁止ファイルが作業の中で変わったらその場で止めて PR を作らない（[ゲート](#ゲート)）
- ほかの固定の除外ファイルは変えても PR は作り、自動マージだけを予約しない

理由

- `MERGE_WHILE_YOU_SLEEP_ALLOW_PATHS` を必須にするのは、固定の除外ファイルを並べるだけでは漏れが残るため ── ビルドの設定、CD の設定、コンテナの定義のように、ゲートやデプロイを変えるファイルはプロジェクトごとに名前が違い、並べきれない。範囲を導入する側が書けば（例: `src/**`）、知らない名前のファイルは範囲の外になる
- 固定の除外ファイルを残すのは、パターンを広く書いたとき（例: `src/` の下に `tsconfig.json` がある）にも、ゲートを外せないようにするため
- 固定の除外ファイルを減らせないのは、そこを開けるとほかの守り（ゲート、Claude Code の決まり、依存の検査）を全部外せるから
- 新しいテストのファイルを範囲に入れるのは、テスト作成の工程が書いたテストが、完了条件を確かめる手段としてマージされる必要があるから
- `MERGE_WHILE_YOU_SLEEP_ALLOW_PATHS` の外の新しいテストのファイルを範囲に入れないのは、テストのパターンが `**/tests/**` や `**/fixtures/**` のように、どの階層でも合うから ── 範囲の外のディレクトリ（例: 配下をそのままデプロイするディレクトリ）に作ったファイルもテストの名前なら範囲に入ってしまう
- 既存のテストを外すのは、既存のテストがこれまでの採点の基準で、変えるかは人が決めることだから
- 範囲の外を変えた実行でも PR を作るのは、人が朝に読んで、そのままマージできるようにするため ── 依存の追加のように範囲の外の変更が必要な Issue もある。変更しそうなことは承認の前に下書きが書いている
- 依存の追加は別の検査ではなく範囲で扱う ── 依存の定義のファイルを範囲の外に置けば、追加したときに人に引き継がれる。照合だけで済む
- TAKT も fork からの PR で CLAUDE.md、AGENTS.md、`.claude/`、`.mcp.json`、`.github/workflows/` の変更を見つけると止める（TAKT の src/features/merge/threat-check.ts）

制約

- 導入のときに変数を1つ書く ── 既定値では動かない。[README の「導入」](../../README.md#導入)に入れる
- 固定の除外ファイルはテストと設定の道具の名前を並べきれない ── `MERGE_WHILE_YOU_SLEEP_ALLOW_PATHS` はソースのディレクトリだけに狭く書く。[README の「Secrets と変数を登録する」](../../README.md#secrets-と変数を登録する)にも書く
- ソースのファイルの中に書くテスト（例: Rust の `#[cfg(test)]` のモジュール）は、パスでテストと見分けられない ── 凍結と既存のテストの確かめの対象にならない。そういうプロジェクトではソースの範囲を `MERGE_WHILE_YOU_SLEEP_ALLOW_PATHS` から外すか、毎回人が PR を読む
- 新しいテストのファイルの中のコードが、既存のテストの前提を変えることは、パスでは見つけられない（例: pytest でテストのモジュールを読み込んだときにほかのモジュールを書き換える。Go でテストのファイルの `init` が同じパッケージの変数を変える）
  - 既存のテストだけのツリーでもう1回テストのコマンドを実行して見つける（[ゲート](#ゲート)）。その分実装と修正のたびにテストの時間が増える
- 範囲の中のソースのコードがテストの実行中だけ違う動きをすることは、コマンドでは見つけられない ── レビューの指示文で見させる
- 依存を追加する Issue は毎回人が PR を読んでマージする
- 確かめるのは提出のジョブで、基準コミットとの差分全体に1回。名前を変えたファイルは変える前と後の両方のパスで確かめる

## 検査のタイミング

正確さと品質を保ったまま速さを落とさないための決まり。検査を毎回実行すると全体が遅くなり、Claude Code の応答も遅くなる

- ツール呼び出しごとに実行するのは、照合だけで済むもの（Claude Code の permission の deny ルール）と、OS が止める sandbox に限る ── hooks（Claude Code のツール呼び出しの前後などに、設定したコマンドを実行する仕組み）や Claude Code による検査をツール呼び出しのたびに挟まない
- 安い順に並べ、失敗したらそこで止めて修正に戻す ── コストの高い検査（Claude Code によるレビュー、ミューテーションテスト）は、安い検査を全部通過したものにだけ実行する
- 結果が変わらない検査は 1回だけ実行する ── 例: 自動マージの範囲は提出のジョブで基準コミットとの差分全体に1回
- 仕組みで起きないようにできるものは検査にしない ── 実行中のコストが無く、すり抜けもない

| 置き場所 | 頻度 | 例 |
|---|---|---|
| 仕組み | 導入時に1回 ── 実行中のコストなし | PR 用トークンは Claude Code が動くジョブに置かない（[security.md の「提出を別のジョブにする」](security.md#提出を別のジョブにする)） |
| 仕組み | 導入時に1回 ── 実行中のコストなし | 手で起動ラベルを付けられるのは triage 以上の権限を持つ人だけ。テンプレートが付けたラベルは Issue を書いた人が付けたものとして、事前確認で権限を確かめる |
| 事前確認 | 実行ごとに1回 | 起動ラベル、権限、承認、リポジトリの設定（一覧は表の下） |
| 作業のジョブの最初 | 実行ごとに1回 | 着手前のゲート |
| ツール呼び出しごと | Claude Code がツールを使うたび | permission の deny ルール、sandbox |
| Claude Code を呼び出す前 | 工程ごと | 変更禁止ファイルが変わっていないか、増えていないか（作業ディレクトリ全体を探して、ハッシュで照合） |
| 工程の区切り | 反復ごと | ゲート |
| 作業のジョブの最後 | 実行ごとに1回 | 差分に認証情報の文字列が無いか |
| 提出のジョブ | 実行ごとに1回 | 差分とコミットの確かめ直し（一覧は表の下） |

事前確認で確かめること

- 起動ラベルが今も付いていて Issue が開いているか
- 付けた人が書き込み権限以上か
- 承認する完了条件があるか
- 起動ラベルのあとに新しい下書きが無いか
- 承認の対象とタイトルが変わっていないか
- auto-merge が有効か
- ワークフローの `GITHUB_TOKEN` の既定が読み取りか
- GitHub Actions に PR の作成と承認を許す設定（Allow GitHub Actions to create and approve pull requests）が外れているか ── 外れていないとワークフローのトークンで PR を承認できる
- マージ先のブランチに必須のステータスチェックがあるか
- マージキューと署名付きのコミットの必須が無いか
- マージの方法が許可されているか
- 使うラベルがあるか（無ければ作る）

提出のジョブで確かめること

- 取り込んだコミットが基準コミットの子孫か
- 自動マージの範囲（シンボリックリンクと gitlink を含む。gitlink はサブモジュールのコミットを指す git の項目）
- 既存のテスト
- 変更禁止ファイル
- 追加した行の無効化の書き方と外の画像
- コミットのメッセージ

検査のタイミングの補足

- 事前確認は Claude Code を呼び出す前に、API の呼び出しだけで済ませる ── 導入の設定が足りないと判明したら、サブスクの利用枠を使う前に止めて、足りない設定を Issue に書く
- 必須のステータスチェックが無いと CI の結果を待たずにマージされる ── auto-merge は「after all required reviews and status checks pass」にマージする（GitHub Docs の [Automatically merging a pull request](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/incorporating-changes-from-a-pull-request/automatically-merging-a-pull-request)）ので、待つ相手が無い
- 認証情報の文字列の照合はこの実行が持つ認証情報をそのまま書き写した場合だけを見つける ── 変形した認証情報は見つけられない
  - 漏れを防ぐ本体は認証情報を読ませないことと、外に送らせないこと（[security.md の「守り」](security.md#守り)）
  - 一般の秘密情報のパターンは誤検出が多く、人への引き継ぎが増えるので使わない

## 上限と繰り返しの検知

人が見ていない前提なので実行が止まらなくなるのを防ぐ仕組みを work.mjs に持たせる

- どれかに達したら人に引き継ぐ
- その時点の変更があれば PR にして（自動マージは予約しない）残す ── 人が朝にどこで止まったかを読め、起動ラベルを付け直せば、その PR の続きから進める

判断: 初期値を次の表のとおりにする。CI の結果を待つ時間と、ブランチを最新にし直す回数のほかは、action の入力で変えられる（[adoption.md の「action ごとの入力」](adoption.md#action-ごとの入力)）。この2つは提出の action の中の決まった値

| 上限 | 初期値 | 決めた理由 |
|---|---|---|
| レビュー → 修正の反復 | 3回 | TAKT のビルトインのワークフローは繰り返しを続けるかの判定を、18か所で3回、8か所で4回に置いている（TAKT の builtins/ja/workflows の `threshold`）。小さい骨格なので短いほうに合わせる |
| 同じ指摘が残り続ける | 同じ ID の指摘が 2回続けて「残っている」 | 3回の上限より前に修正できていないことが判明する |
| ゲートの失敗 → 修正 | 1回の反復の中で3回 | ゲートの失敗は具体的な出力があって修正しやすい。それでも3回続くなら修正できていない。テスト作成のゲートが失敗してテスト作成をやり直すときも同じく3回 |
| テスト作成に戻す | 1回 | 実装か修正の工程が「テストが間違っている」と返したときと、ミューテーションテストが失敗したときの合計 |
| 下書きの質問 | 質問を返した下書き5回（数え方は表の下） | 5回聞いて決まらない依頼は完了条件が足りないとして人に引き継ぐ |
| 実行のコスト | 1回の実行で 15 USD（Claude Code の推定） | 止める目安。小さい課題で測った1回の実行は 0.34〜0.47 USD（[results.md](results.md#測定結果)）で、大きい課題の実測は無い |
| 作業のジョブの時間 | 120分（ジョブの開始から数える。準備と着手前のゲートの時間も含む） | ジョブの6時間より十分短くし、ジョブの最後の処理（引き継ぎのコメント、変更の受け渡し）の時間を残す |
| 下書きの時間 | 下書きの Claude Code の呼び出し1回で20分 | コードを読んでコメントするだけ |
| 下書きのコスト | 1回の下書きで 2 USD（Claude Code の推定） | 下書きは triage 以上の人がコメントするたびに動く。止める目安で、下書きのコストは測っていない |
| CI の結果を待つ時間 | 1回の提出で合計90分 | 再実行とブランチを最新にし直した分も含める。提出のジョブが待つ間、後ろの実行は実行待ちのままなので長く待たせない |
| ブランチを最新にし直す | 3回 | 夜のうちに main が何度も進むと繰り返しになる |

下書きの質問の数え方

- 数えるのは最後に下書きラベルを付けたあとの下書き
- 1回の下書きで質問が複数あっても1回
- 質問の無い下書きは数えない

ジョブの `timeout-minutes`

- どのジョブにも `timeout-minutes` を書く ── 作業は150分、提出は120分、下書きは30分、実行待ちの通知、事前確認、終了処理は10分
- work.mjs の時間の上限が機能しない止まり方（runner の不調など）でも、ジョブの既定の6時間まで残らない。時間切れは終了処理が「途中で終わった」として引き継ぐ
- 作業のジョブの時間の上限を上げるときはテンプレートの `timeout-minutes` も、上限より30分ほど長く上げる
- 下書きのジョブの時間の上限を上げるときはテンプレートの `timeout-minutes` も上げる

上限の補足

- コストの上限は Claude Code の呼び出しごとに `--max-budget-usd` へ残りの額を渡して守る ── [CLI reference](https://code.claude.com/docs/en/cli-reference) に推定は請求額と違うことがあり、上限を超えることもあるので、余裕を残すよう書かれている
- 1回の呼び出しのターン数（`--max-turns`）は制限しない ── コストと時間の上限で止まる
- サブスクの利用枠の上限に達して Claude Code が止まったときも上限に達したとして引き継ぐ ── 次にやることは利用枠が戻ってから起動ラベルを付け直すこと
- TAKT は同じステップが10回を超えて続いたら繰り返しとみなす（TAKT の src/core/workflow/engine/loop-detector.ts の既定値 `maxConsecutiveSameStep: 10`）。この設計は工程の並びが決まっているので、反復の回数と同じ指摘の残り方で見る

実装のときに確かめること

- サブスクの利用枠の上限に達したとき `claude -p --output-format json` の結果にどう出るか ── 理由を見分けて、引き継ぎのコメントに書く
