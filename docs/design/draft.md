# 完了条件の下書き

Issue から完了条件を下書きし、人が承認するまで。設計書の入口は [README.md](README.md)

判断: 人はやりたいことを Issue に書くだけにする。[Claude Code](https://code.claude.com/docs) がコードを読んで完了条件の案と質問を Issue にコメントし、人はコメントで答え、案でよければ起動ラベルを付けて承認する

人の操作の数

| 場合 | 人の操作 |
|---|---|
| 通常（質問が無い） | 2つ ── やりたいことを書く、承認する |
| 質問があるとき | 3つ ── 答えるが1つ増える |
| 止まったとき | 人への引き継ぎで1回増える |
| 人が完了条件まで書いた Issue | 1つ ── 書くことが承認を兼ねる（[人が完了条件を書く場合](#人が完了条件を書く場合)） |

承認の1つより減らさない ── Claude Code が書いた完了条件を人が読まずに採点の基準にすると、Claude Code が書いた完了条件で Claude Code が採点する形に戻る

人の操作は GitHub の画面だけで済み、スマートフォンからでも、時間を空けても回答できる

下書きに書くこと

- 完了条件 ── 1項目ずつテストで確かめられる形で書く。テスト作成とレビューはこの項目ごとに確かめる
- 今回やらないこと ── 範囲の取り違えを承認の前に見つけられる
- 自動マージの範囲の外を変更しそうか ── 変更しそうなら承認の前に「人が PR を読む必要がある見込みです」と書く。寝る前に確認できる
- 質問 ── コードを読めば判明することは聞かない。聞くのは人にしか決められないことだけ
- 大きすぎる依頼なら、Issue を分ける案

下書きのコメントは、draft.mjs が Claude Code のレポート（JSON）から組み立てる。画面に表示されない文字は除く（[run.md の「指示文と Claude Code に渡すもの」](run.md#指示文と-claude-code-に渡すもの)）── 承認の記録が、人が画面で読んだ内容と一致する

完了条件と今回やらないことは、Markdown として解釈されない形（コードブロック）で書く ── Markdown には画面に表示されない書き方がある（[GitHub Flavored Markdown の仕様](https://github.github.com/gfm/) の 4.7 に「A link reference definition does not correspond to a structural element of a document.」。画像の代替テキストとリンクの title も本文には表示されない）。コードブロックなら書いた文字が全部画面に表示される

外部の投稿者が書いた Issue とコメントの扱いは [security.md の「外から来る文面」](security.md#外から来る文面)に書く

制約

- 工程が1つ増える

## 下書きの開始条件

判断: 下書きラベルを付けた人が triage（GitHub のリポジトリのロールの1つ。Issue と PR のラベルを付けられるが、コードは書き込めない）以上の権限を持つときに下書きを始める。起動ラベルが付いていない、開いている Issue に限る

- 下書き用の Issue のテンプレートで作った Issue にはテンプレートが下書きラベルを自動で付ける ── このときは、Issue を書いた人がラベルを付けたものとして扱う
- テンプレートを使わなかった Issue は権限のある人があとから下書きラベルを付けたら始める
- ラベルを付けたのが人のアカウントのときだけ始める（イベントの `sender.type` が `User`）── ほかの GitHub App や bot が付けたラベルでは動かない
- 下書きラベルを付けたあとに、triage 未満の人が Issue のタイトルか本文を変えていたら下書きをせずに人に引き継ぐ ── 権限のある人が読んでラベルを付けたときの内容と、Claude Code に渡す内容を揃える
  - 本文は GraphQL API の Issue の `editor`（Issue が実装する `Comment` のインターフェースの説明に「The actor who edited the comment.」）と `lastEditedAt`、タイトルは `RenamedTitleEvent` の `actor` と `createdAt` で見る（GitHub Docs の [GraphQL の Issues のリファレンス](https://docs.github.com/en/graphql/reference/issues)）
  - `editor` は最後に編集した人なので、そのあとに権限のある人が編集していれば、読んだものとして扱う

下書き中の扱い

- 下書き中の Issue は下書きラベルが付いていて、起動ラベルが付いていない Issue。triage 以上の権限を持つ人がコメントするたびに下書きをし直す
- 1回の下書きは前の下書きのあとに付いた、triage 以上の権限を持つ人のコメントを全部まとめて読む ── コメントが続けて付くと、下書きのジョブが concurrency のグループで順に待って続くが、2つ目からは読むコメントが無く、Claude Code を呼び出さずに終わる
- 下書きのジョブはコメントを書く直前に起動ラベルを確かめ直し、付いていたら書かない ── 人が承認した下書きのあとに別の下書きが投稿されないようにする。確かめた直後にラベルが付くすれ違いは事前確認が見つけて止める（[承認の記録](#承認の記録)）
- 事前確認が承認を記録したら下書きラベルを外す ── そのあとのコメントでは下書きをし直さない。し直したいときは下書きラベルを付け直す
- 下書きラベルを付けた（付け直した）イベントでは読むコメントが無くても下書きをし直す ── 人への引き継ぎの次にやることが「下書きラベルを付け直す」なので、付け直して何も起きない形にしない
- 下書きの質問の上限は最後に下書きラベルを付けたあとの下書きの回数で数える（1回の下書きで質問が複数あっても1回）

| 案 | 人の操作（通常） | 外部の投稿者の Issue | メモや議論の Issue |
|---|---|---|---|
| 下書きラベルと起動ラベルを毎回両方付ける | 3つか4つ | 下書きラベルが付くまで動かない | 動かない |
| 書き込み権限以上の人が書いた Issue は全部すぐ始める | 2つか3つ | 下書きラベルが付くまで動かない | 動いてしまう |
| テンプレートの下書きラベルと、ラベルを付けた人の権限で決める（選んだ案） | 2つか3つ | 下書きラベルが付くまで動かない | 動かない |
| 起動ラベル1つで付けるたびに次へ進む | 2つか3つ（付け直しを含む） | 起動ラベルが付くまで動かない | 動かない |

理由

- テンプレートで作ればラベルが自動で付くので、人の操作が増えない ── GitHub Docs の [Syntax for issue forms](https://docs.github.com/en/communities/using-templates-to-encourage-useful-issues-and-pull-requests/syntax-for-issue-forms) に、`labels` は「Labels that will automatically be added to issues created with this template.」
- メモや議論の Issue はテンプレートを使わなければ下書きの対象にならない
- 外部の投稿者がテンプレートで Issue を作ると下書きラベルは付くが、付けたのが外部の投稿者なので始めない ── ラベルを付けた人の権限で決める。権限のある人が読んで付け直したら始める
- 起動ラベル1つで進める案は、同じラベルが状態によって違う意味になり、いま何をしたことになるのかを人が把握しにくい
- 権限は GitHub の API で確かめる ── GitHub Docs の [Get repository permissions for a user](https://docs.github.com/en/rest/collaborators/collaborators#get-repository-permissions-for-a-user) に、`permission` は「the legacy base roles of admin, write, read, and none,」で triage は read として返る。`role_name` は「the name of the assigned role, including custom roles.」
  - 書き込み権限以上は `permission` が admin か write で、triage は `role_name` で見分ける
  - triage を元にしたカスタムのロールは `role_name` がそのロールの名前になるので、triage 未満として扱う ── 下書きを始めない側に寄せる。その人には下書きラベルを権限のある人に付けてもらう

制約

- 下書きラベルがリポジトリに無いとテンプレートでも付かない（同じページに「If a label does not already exist in the repository, it will not be automatically added to the issue.」）── [README の「ラベルを作成する」](../../README.md#ラベルを作成する)で使うラベルを3つ作る
- ラベルの名前を変数で変えたらテンプレートの `labels` も同じ名前に修正する（テンプレートには決まった文字列で書く）
- 導入する側は下書き用の Issue のテンプレートもコピーする

## 人が完了条件を書く場合

判断: 書き込み権限以上の人が完了条件の欄のある Issue のテンプレートで Issue を作ったら、下書きを飛ばして実行する。このテンプレートは起動ラベルを自動で付ける

- Issue を書いて作成することが承認を兼ねる ── 完了条件を書いたのは人なので、Claude Code が書いた完了条件で Claude Code が採点する形にならない
- 人の操作は1つ ── Issue を書いて作成する
- 外部の投稿者がこのテンプレートを使っても、起動ラベルを付けたのが外部の投稿者なので実行しない（事前確認で、ラベルを付けた人の権限を確かめる）
- 下書きを飛ばすのは起動ラベルを付けた人が Issue を書いた人のときだけ ── 別の人が書いた完了条件の欄は画面に表示されない書き方（リンクの参照定義、画像の代替テキスト）で内容を追加できる
  - 権限のある人が、別の人がテンプレートで書いた Issue に起動ラベルを付けたときは承認する完了条件が無いとして止め、下書きラベルを付けるようコメントする

理由

- 依頼する人が完了条件まで自分で決められることがある（例: バグの再現手順と期待する結果が判明している）── 下書きのやり取りを待つ理由が無い
- 完了条件を決まった欄に書かせると本文のどこを完了条件として読むかが決まる

制約

- 完了条件が足りなくても質問されないまま進む ── 計画、テスト作成、実装の工程のどれかが「完了条件が足りない」と返したら人に引き継ぐ
- 導入する側がコピーする Issue のテンプレートが2つになる

確認結果（GitHub ホストの runner `ubuntu-24.04`。1回）

- Issue forms で作った Issue の本文から完了条件の欄の内容を切り出せる ── 承認の記録の `source` が `template` になり、完了条件の欄の4行がそのまま入った
- テンプレートが付けた起動ラベルの `LabeledEvent` の `actor` は、Issue を書いた人になる

## 承認の記録

判断: 事前確認が承認された完了条件を Issue へのコメントとして記録する。承認のあとの工程と、提出が組み立てる PR の本文は、この記録だけを使う

記録するもの

- 下書きから来た Issue: 起動ラベルを付けた時刻より前に書かれた、最後の下書きのコメントにある完了条件
- 完了条件を人が書いた Issue: テンプレートの完了条件の欄
- どちらも: Issue のタイトル、起動ラベルを付けた人、付けた時刻

下書きのコメントとして読むのは、次の4つが全部合うものだけ

- 書いたのが github-actions[bot]
- 本文の目印に、書いた下書きのジョブの実行の番号（`run_id`）がある
- その実行が下書き用のワークフローのファイルのもの ── Actions の API で実行のワークフローのファイルのパスを確かめる（GitHub Docs の [REST API endpoints for workflow runs](https://docs.github.com/en/rest/actions/workflow-runs) の Get a workflow run が `path` を返す）
  - その実行の `event` が `issues` か `issue_comment` で、`head_branch` が default ブランチであることも確かめる ── 同じパスのファイルでも別のブランチやイベントで起きた実行がありうる
- その実行が残した artifact（ワークフローの実行に付けて保存するファイル。ジョブの間とワークフローの間の受け渡しに使う）に、そのコメントの ID と本文のハッシュがある ── 下書きのジョブはコメントを書いたあとに、ID と本文のハッシュを artifact にする（保持期間は30日）

artifact まで確かめる理由と、消えていたとき

- 同じリポジトリのほかのワークフローも、`GITHUB_TOKEN` でコメントすると github-actions[bot] の名義になり、本文に何でも書ける ── 名義と目印だけではほかのワークフローが Issue の文面をコピーしたコメントと見分けられない
- GitHub の REST API には artifact を作る操作が無く（[README.md の「構成」](README.md#構成)）、ほかのワークフローの実行から、この実行に artifact を追加する手段は見つかっていない（推論のみ）
- artifact が期限で消えていたら始められないとして止める（下書きラベルを付け直せば新しい下書きから始められる）

事前確認は承認の記録をジョブの出力で作業と提出のジョブに渡す ── あとのジョブは、Issue のコメントを読み直さない

事前確認が確かめること

- 起動ラベルが今も付いていて、Issue が開いているか ── 外れていたら人が取り消したものとして、引き継がずに終わる。実行待ちの間に起動ラベルを外せば実行を取り消せる
- 起動ラベルを付けた人が書き込み権限以上か（[adoption.md の「起動方法」](adoption.md#起動方法)）── ほかの確かめより先に、`GITHUB_TOKEN` で確かめる。満たさなければ、PR 用トークンを発行しない
- 見るのは今付いている起動ラベルを付けた、最新の `LabeledEvent` 1つ ── 付けた人の権限と、下の比べ方の時刻を同じイベントで見る
  - 別々のイベントで見ると、権限のある人が付けたあとに承認の対象が編集され、triage の人が付け直したとき、誰も承認していない内容が承認の記録に入る
  - そのイベントがこの実行を起こしたものでなければ（実行待ちの間に付け直された）、この実行は何もせずに終わり、付け直したラベルの実行に任せる
  - 見分け方: 最新の `LabeledEvent` の `createdAt` がこの実行の作られた時刻（Get a workflow run の `created_at`）より後なら付け直されたとみなす
- 起動ラベルを付けたあとに新しい下書きのコメントが書かれていないか ── 書かれていたら、人が読んでいない完了条件があるので、実行せずに人に引き継ぐ
- 承認の対象（最後の下書きのコメント、またはテンプレートで書いた Issue の本文）が、起動ラベルを付けたあとに編集されていないか ── GitHub の [GraphQL API](https://docs.github.com/en/graphql) で、コメントと Issue の `lastEditedAt`（最後に編集された時刻）と、ラベルを付けた `LabeledEvent` の `createdAt` を比べる。編集されていたら実行せずに人に引き継ぐ
- Issue のタイトルが起動ラベルを付けたあとに変えられていないか（`RenamedTitleEvent` の `createdAt`）── タイトルは承認の記録に入り、計画からあとの工程に渡る
- 承認する完了条件があるか ── 下書きも、完了条件の欄も無ければ、実行せずに人に引き継ぐ。コメントに、下書きラベルを付ければ下書きを始めると書く

理由

- 実行待ちの間に承認の対象が編集されうる ── 記録した時点で内容が決まり、そのあとで Issue が編集されても、採点の基準は変わらない
- 承認のあとの工程に、Issue の本文とコメントを渡さずに済む（[run.md の「指示文と Claude Code に渡すもの」](run.md#指示文と-claude-code-に渡すもの)）
- 続きから進めるかを前の実行の記録と比べて決められる（[run.md の「再実行」](run.md#再実行)）
- 記録は github-actions[bot] のコメントで、編集できるのは書き込み権限以上の人だけ ── GitHub Docs の [Managing disruptive comments](https://docs.github.com/en/communities/moderating-comments-and-conversations/managing-disruptive-comments) に「Anyone with write access to a repository can edit comments on issues, discussions, pull requests, and commits.」

制約

- 起動ラベルを付けたあとに承認の対象を修正すると誤字の修正でも止まる ── 起動ラベルを付け直せば修正したあとの内容で記録する
